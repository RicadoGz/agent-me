# 开发前先说清楚

让用户在动代码前明白实际要做什么、需要自己决定什么、可以学到什么，以及交付时怎么检查。

## 先看事实

读取当前进度、对应功能计划和必要代码，核对现有行为、需求、关键失败情况与依赖。内部认真审查设计和可能的 Bug。阅读范围以回答当前任务为界。

区分已实现、实际验证过和仍拟议的内容。影响方案的未验证假设要直说。已经有的机制作为现有基础，不包装成新的待开发功能。

## 四项说明

默认用简单中文，每项一小段。用户指定其他语言或字数时遵从当前要求。长度以把操作过程讲清楚为准，单次的 200 字限制不成为永久默认。

1. **Plan：准备怎么做。** 先说目前有什么、缺什么，再讲这次的改动和边界。按“用户做一个动作，程序处理什么，最后看到什么”解释核心逻辑。涉及后端、保存或状态同步时，说明影响结果的那一步。用具体操作代替函数清单和架构口号。
2. **Decision：哪些需要用户决定。** 只列重要且尚未确认的产品、范围、数据后果、费用或授权选择。给明确建议并说明取舍。普通技术选择自己处理；已确认的选择直接承接。没有新决定就明说，不制造确认问题。
3. **Learning：教一个点。** 选择本次工作中值得理解的一个技术点，用大白话和当前功能的小例子说明它解决什么问题。术语随后补充。承接用户已经表现出的理解，选择其下一步需要理解的内容；用户已讲清的概念无需反复换名称讲解。教学深度由用户后续兴趣展开。
4. **Verification：怎么证明正常。** 说明会做什么操作、应看到什么结果，以及最重要的失败情况如何检查。复用足够的既有检查，只补实际缺口；区分计划中的验证和已经运行的结果。界面行为、持久化或真实外部执行要有各自对应的证据。

## 说明之后如何行动

1. 用户要求“只检查”“先规划”“不要实现”时，完成说明后停在审查或方案阶段，不改产品代码。创建本 skill 的请求也不授权其中举例的产品开发。
2. 任务已经授权实施、范围明确且没有重要未决决定时，先发说明，再继续执行，无需增加一次批准流程。
3. 存在重要未决决定时，明确问题与建议，等待答案再做依赖它的工作。继续推进其他已授权且不依赖答案的部分。
4. 同一范围内已说明并获确认的内容不在每次工具调用或小步骤前重讲。范围发生实质变化时，补充变化及其影响。

## 表达示例

用户要求给待办增加编辑功能时，可这样解释核心逻辑：

“你点开一条待办，修改文字再保存。后台先检查这条待办有没有被其他页面改过，版本没变才保存；如果已经被改过，就保留你输入的内容并提示刷新，避免旧页面把新内容盖掉。”

学习点可顺着这个例子解释“版本号像修改次数，保存时先对一下”，而不是只列出“乐观锁、状态管理、数据库更新”等术语。具体方案仍以实际代码和已确认需求为准。
